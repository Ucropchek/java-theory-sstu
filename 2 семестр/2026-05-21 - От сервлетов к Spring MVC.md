# От сервлетов к Spring MVC - секьюритизированная версия

**Лекция от 21 мая 2026 года**

Главный вопрос: где находится `DispatcherServlet`, зачем он нужен и как HTTP-запрос доходит до метода Spring-контроллера? Для ответа нужно разделить три задачи: приём запроса сервером, выполнение прикладной логики и формирование ответа.

## 1. Как запрос обрабатывается без Spring MVC

Рассмотрим приложение, развёрнутое в Apache Tomcat. Tomcat выступает контейнером сервлетов: принимает HTTP-запросы и передаёт их компонентам приложения. На одном сервере могут работать разные приложения; внутри выбранного приложения запрос сопоставляется с зарегистрированным сервлетом.

Упрощённая последовательность выглядит так:

```text
Клиент → Tomcat → веб-приложение → выбранный сервлет
                                      ↓
                                  service()
                                      ↓
                            doGet(), doPost() и т. д.
                                      ↓
                                HTTP-ответ
```

HTTP-сервлет обычно создают как наследника `HttpServlet`. Это **абстрактный класс, а не интерфейс**. Его метод `service()` определяет HTTP-метод запроса и вызывает соответствующий обработчик: `GET` направляется в `doGet()`, `POST` в `doPost()`, `PUT` в `doPut()`, `DELETE` в `doDelete()`. Выбор происходит по HTTP-методу, а не по сигнатуре произвольного Java-метода.

В обычном прикладном сервлете переопределяют нужные `doXxx()`. Собственную реализацию `service()` писать, как правило, незачем. В обработчик передаются `HttpServletRequest` для чтения запроса и `HttpServletResponse` для формирования ответа. См. [документацию HttpServlet](https://jakarta.ee/specifications/servlet/6.1/apidocs/jakarta.servlet/jakarta/servlet/http/HttpServlet.html).

Сопоставление URL и сервлета называется *servlet mapping*. Его можно задать в `web.xml`; XML не является обязательным единственным способом регистрации.

## 2. Почему одних сервлетов неудобно

Servlet API даёт доступ к HTTP, но не решает за приложение, что означают полученные данные. Если в теле запроса находится JSON с данными студента, его нужно прочитать и преобразовать в Java-объект. Затем нужно вызвать прикладную логику, выбрать статус ответа и записать результат в подходящем формате.

Схематически ручная обработка выглядит так:

```text
Прочитать тело запроса
→ разобрать JSON
→ получить объект Student
→ выполнить нужную операцию
→ преобразовать результат в JSON
→ записать ответ
```

Библиотека сериализации, например Jackson, снимает часть работы, но её вызовы и обработка ошибок всё равно должны быть организованы. При большом количестве обработчиков повторяется инфраструктурный код.

Для HTML появляется ещё одна проблема. Если собирать страницу последовательными вызовами `writer.append(...)`, в одном методе смешиваются бизнес-логика, структура страницы и HTTP-взаимодействие. Изменять разметку трудно, а проверять прикладные правила отдельно от представления неудобно.

Отсюда две задачи будущего решения:

1. Централизовать повторяющуюся обработку запросов и ответов.
2. Отделить прикладную логику от способа её отображения.

## 3. Контейнер сервлетов и контейнер Spring

В лекции речь идёт о двух разных значениях слова «контейнер»:

- **Контейнер сервлетов**, например Tomcat, обеспечивает выполнение сервлетов и обработку HTTP.
- **Контейнер Spring**, представленный контекстом приложения, управляет бинами и их зависимостями.

Обычный Spring-бин ещё не является HTTP-обработчиком. Если поставить на класс только `@Component`, Tomcat не начнёт самостоятельно направлять в его методы запросы.

Для интеграции нужен компонент, который понятен контейнеру сервлетов и одновременно использует инфраструктуру Spring. В Spring MVC эту роль выполняет **`DispatcherServlet`**. Это настоящий сервлет и центральная точка диспетчеризации запросов, то есть реализация шаблона *Front Controller*.

Его регистрируют в контейнере сервлетов и назначают ему URL mapping. Затем он использует Spring-контекст и настроенные компоненты обработки. Это не обязательно единственный сервлет приложения: «один центральный сервлет» описывает подход, а не ограничение платформы. Контекст не создаётся заново для каждого запроса.

В Spring Boot запуск и регистрация обычно организуются автоматически при подходящей конфигурации веб-приложения. В приложении без Boot их можно настроить явно. См. [DispatcherServlet](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet.html).

## 4. Как выбирается метод контроллера

После перехода к Spring MVC прикладному обработчику обычно не требуется наследовать `HttpServlet`. Разработчик создаёт контроллер и описывает маршруты аннотациями.

```text
HTTP-запрос
    ↓
Tomcat и servlet mapping
    ↓
DispatcherServlet
    ↓
HandlerMapping: какой обработчик подходит?
    ↓
HandlerAdapter: как вызвать этот обработчик?
    ↓
Метод контроллера → прикладной сервис
```

`HandlerMapping` сопоставляет запрос с обработчиком. Для аннотированных контроллеров учитываются условия `@RequestMapping` и её специализированных вариантов, например `@GetMapping`.

`HandlerAdapter` обеспечивает вызов найденного обработчика. Для метода контроллера инфраструктура Spring подготавливает аргументы и обрабатывает возвращённое значение. Поэтому диспетчеру не требуется самому реализовывать все особенности вызова каждого типа обработчиков.

`DispatcherServlet` и прикладной контроллер не одно и то же: первый координирует общий процесс, второй обрабатывает конкретный сценарий. См. [специальные компоненты Spring MVC](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet/special-bean-types.html).

## 5. Что означает MVC

**MVC** расшифровывается как *Model, View, Controller*: модель, представление и контроллер. Смысл разделения в том, чтобы изменение интерфейса не требовало переписывать прикладные правила, а изменение правил не сводилось к редактированию разметки.

Для серверного веб-приложения роли можно описать так:

- **Контроллер** принимает запрос, обращается к прикладной логике и определяет результат обработки.
- **Модель для представления** содержит данные, необходимые при построении ответа.
- **Представление** формирует отображение этих данных, например HTML-страницу.

Здесь важно различать два употребления слова «модель». Модель предметной области включает сущности и правила приложения. Объект Spring `Model`, передаваемый в метод контроллера, служит для передачи именованных атрибутов представлению. Это не вся бизнес-логика приложения и не база данных.

В интерфейсах с графиками и элементами управления изменение модели может сопровождаться уведомлением представлений. Однако переносить такую схему буквально на серверную HTML-страницу нельзя. В рассматриваемом веб-сценарии сервер обрабатывает запрос, формирует страницу и отправляет результат. Шаблон сам по себе не подписывается на изменения Java-объектов в серверной памяти.

## 6. Контроллер, модель и HTML-шаблон

Учебный пример контроллера:

```java
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.GetMapping;

@Controller
public class StudentPageController {

    @GetMapping("/student")
    public String studentPage(Model model) {
        model.addAttribute("studentName", "Алексей");
        return "student";
    }
}
```

Здесь `/student` является маршрутом запроса, `studentName` является именем атрибута модели, а строка `student` является логическим именем представления. Это три разные вещи.

В типичном Spring Boot-приложении с подключённым Thymeleaf шаблон размещают в `src/main/resources/templates/student.html`:

```html
<!DOCTYPE html>
<html lang="ru" xmlns:th="http://www.thymeleaf.org">
<head>
    <meta charset="UTF-8">
    <title>Студент</title>
</head>
<body>
    <h1 th:text="${studentName}">Имя студента</h1>
</body>
</html>
```

Шаблонизатор подставляет значение атрибута в HTML. Клиент получает готовую страницу, а не Java-объект `Model`. Папка `templates` предназначена именно для шаблонов; это не обозначение «файлов, которым не требуется заполнение». Имя представления обычно возвращают без расширения, а путь и суффикс определяются конфигурацией. См. [пример Spring MVC с Thymeleaf](https://spring.io/guides/gs/serving-web-content/).

Последовательность формирования страницы:

```text
Контроллер заполняет Model и возвращает имя представления
→ ViewResolver находит подходящий View
→ View использует модель и шаблон
→ формируется HTML
→ клиент получает HTTP-ответ
```

Возврат представления не обязателен для каждого обработчика: Spring MVC поддерживает и непосредственное формирование тела ответа. См. [последовательность обработки](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet/sequence.html).

## 7. Ответ с данными вместо готовой страницы

Другой вариант: сервер возвращает данные, а интерфейс строит клиент. Такой API может использоваться браузерным, мобильным или настольным приложением.

```java
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class StudentApiController {

    public record StudentDto(long id, String name) {}

    @GetMapping("/api/student")
    public StudentDto student() {
        return new StudentDto(1L, "Алексей");
    }
}
```

При настроенной JSON-конвертации ответ может выглядеть так:

```json
{"id":1,"name":"Алексей"}
```

`@RestController` объединяет `@Controller` и `@ResponseBody`. Возвращаемое значение передаётся в тело ответа через подходящий `HttpMessageConverter`, а не трактуется как имя HTML-представления. JSON является распространённым вариантом, но не единственным возможным форматом.

И обратное: `@Controller` не означает «всегда возвращает имя страницы». Отдельный метод такого контроллера может использовать `@ResponseBody`. См. [семантику @ResponseBody и @RestController](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/responsebody.html).

### MVC и REST не взаимоисключающие технологии

Spring MVC является веб-фреймворком, который обслуживает и HTML-страницы, и HTTP API. REST является архитектурным стилем взаимодействия. Поэтому API на `@RestController` может работать на той же инфраструктуре Spring MVC и через тот же `DispatcherServlet`.

Одна аннотация или возврат JSON ещё не делают API RESTful. REST предполагает архитектурные ограничения, включая единообразный интерфейс и отсутствие зависимости запроса от сохранённого сервером контекста предыдущих клиентских запросов. См. [описание REST Роя Филдинга](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm).

Разделение клиента и сервера также не обязывает создавать два репозитория или два отдельно развёрнутых приложения. Это решение об организации системы. Главная полезная мысль лекции: одна прикладная логика может обслуживать разные интерфейсы. Для этого её следует отделять от HTTP и от шаблонов, например размещая в сервисах.

## 8. Запрос, соединение и сессия

Эти понятия нельзя смешивать:

- **Запрос и ответ** составляют отдельное HTTP-взаимодействие.
- **Сетевое соединение** является транспортом; его время жизни не обязано совпадать с одним запросом.
- **HTTP-сессия** связывает несколько запросов клиента и позволяет сохранять между ними состояние на сервере.

`HttpSession` относится к Servlet API и управляется контейнером. Это не поле, автоматически принадлежащее одному экземпляру `HttpServlet`, и не само соединение. Сессия может переживать несколько соединений и запросов; для её идентификации обычно используются cookie. См. [HttpSession](https://jakarta.ee/specifications/servlet/6.1/apidocs/jakarta.servlet/jakarta/servlet/http/HttpSession.html).

У сервлетного стека нет универсального правила «ответить за одну секунду, иначе отключение». Ограничения зависят от настроек клиента, сервера, прокси и конкретной операции.

Длительные вычисления требуют продуманной организации, но не обязательно отказа от Spring MVC. Он поддерживает асинхронную обработку, например через `Callable` и `DeferredResult`. Асинхронность не отменяет тайм-ауты и не делает вычисление бесплатным. См. [асинхронные запросы Spring MVC](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html).

## 9. Главное для ответа на занятии

`DispatcherServlet` нужен как центральный обработчик на границе Servlet API и Spring MVC. Tomcat направляет в него запрос по servlet mapping. Затем инфраструктура Spring выбирает прикладной обработчик, подготавливает аргументы и вызывает метод контроллера. Контроллер обращается к бизнес-логике и возвращает результат.

Далее возможны два основных учебных сценария:

1. **HTML:** данные модели и имя представления → выбор `View` → обработка шаблона → готовая страница.
2. **API:** возвращённый объект → преобразование в тело ответа → данные для клиента.

Spring MVC не устраняет сервлеты: он строит над ними более удобный механизм, позволяющий не повторять одну и ту же инфраструктурную работу в каждом обработчике.

  И где-то тут, примерно в 2001 году, появляется множество людей, которые задаются вопросом: «А можно писать без лопаты говна во рту?» Spring в этот момент — один из инструментов, который появляется, и он выстреливает тогда и становится популярным. «Мальчик, который выжил»: сегодня Spring, которая просто везде получилась. Насколько она всех достала, что начинаются вопросы: «А что может уйти от неё?» Самая известная альтернатива — Quarkus, так как он большой и тяжёлый, а хочется реактивно и быстро. Spring предлагает титульную — DI, контейнер внедрения зависимостей и т. п. Это только база для реализации вот этого всего HTTP и прочего.

  Просто взять и повесить на HTTP компонент не получится, так как в данном случае получаются два отдельных контейнера: томкатный с сервлетами и отвечающий за перераспределение запросов. Его задача — получить байтовый запрос, распарсить, найти сервлет, отправить в сервлет это. Если повесить компонент на класс, не сработает всё внедрение зависимостей. Надо как-то сделать так, чтобы управление передавалось в Spring-контейнер, а не в сервлет, а уже Spring-контейнер у себя выполнил распределение.

  В этом смысле первая базовая идея — куда-то на что-то повесить компонент, чтобы у нас в итоге-то попадало управление в Spring-контейнер. А что, если в моём приложении будет ровно один сервлет (`DispatcherServlet`), а уже внутри сервлета будет подниматься Spring-контекст? Внутри него уже и контекст поднимаем через `new`, и `service()`, который обрабатывает вообще всё. И в рамках контекста мы должны выбрать бин, который отрабатывать должен: у тебя будет множество компонентиков, среди которых мы найдём тот, который нам нужен.

  Приходит на сервлет, с него на Tomcat, с него на диспетчер-сервлет. Сервлет смотрит на контекст и должен выбрать то, что должно обработать его. Контекст. Выделен спец. тип компонентов — контроллер. Выбираться будет не из всех компонентов, а из тех, которые помечены аннотацией «контроллер». Когда те приходит, диспетчер-сервлет говорит те путь, а ты по пути уже сверяешь, какой контроллер.
- Но мы всё ещё не решили разделение представления и логики (**НЕ ХОЧУ ПИСАТЬ HTML В GET/POST**).
Автор чё-то там, то-сё, вспоминает, что есть концепция MVC, которая существует с 1979. Модель, вью, контроллер. Родилась она в штуке Spark Labs (инфа из фильма — как рождалась компания Apple). Если там исторически смотреть, эта лаба находится в компании про Xerox, а по факту в ней разрабатывали графический интерфейс, а к нему — манипуляторы и язык программирования. По сути, всё то, чем мы сейчас пользуемся: окошки, мышки и т. п. Туда на экскурсию приехал Стив Джобс и в страхе выбежал со словами: «Надо это всё делать самому».

В рамках этого они разрабатывали свой язык — Smalltalk. Предлагал встроенный концепт разделения логики, представления, управления. Предполагалось, что окошечко, на нём контроллер (кнопочка), и у тебя одновременно несколько картинок поменялось. Это надо сделать, но это нельзя жёстко связать (крутилку крутишь, и графики меняются, к примеру). Он предлагал ООП как другую: объект — это состояние, поведение и **СООБЩЕНИЕ**. Предполагался Observer, и ты на любое действие в нём публикуешь сообщение. Там есть подписчики, и получается такой концепт: ты крутишь крутилку — она опубликовала сообщение; менюшки-графики сообщение приняли (прочитали) и поменялись. Крутилка — это контроллер, вью — это графички. Где модель?

(Не очередь сообщений.) Логика говорит так: да, логика должна быть, но вешать на контроллер и вью это — это херня. По факту модель-то — набор классов с бизнесовой логикой. Контроллер ходит в модельку и вызывает методы, которые меняют состояние сообщения. Модель уже занимается выкладкой сообщений — публикацией. Сообщение приходит на вью, она получает и вычитывает из модели всё, чё ей надо, и меняется так, как надо. Крутилка ходит в модель, меняет модель; модель опубликовала месседжи; все, кто подписался на модель, получили сообщение, сходили в модельку, получили данные, поменялись.

AWT, Swing, JavaFX — инструменты, работают, но работают крайне странно. MVC был признан обосрышем, и развивались MVP и MVVM (ViewModel). Но проблема в том, что всё это пригодно только для кнопочек, менюшечек, крутилок и т. п. Ты прокрутил крутилку — сворфиррмалсч респонс, а в ответ тебе респонс.

MVC в данном случае называется Spring Web MVC, который выглядит хитрее. Всё ещё есть контроллер, который входной класс, обрабатывающий твои запросы, — фронт-контроллер иногда называют — диспетчер-сервлет наш. У тебя как бы начало получается такое же, но не совсем. Далее должна быть модель представления — HTML-страница, которую надо сгенерить. Получается, приходят данные на фронт-контроллер, а ты возвращаешь HTML. С помощью фронт-контроллера ты заполняешь модели, а HTML ходит в модель и заполняет себя. Представление — страничка одна.
Страничка сама себя заполнить не может: нужен шаблонизатор, template engine.

Классическое образование идёт с тех времён, когда у нас были гум. науки. В них была передача древних мемов из поколения в поколение. Ты начинаешь изучение с отсылок на «Анабасис» — древнегреч. произведение, где наёмников обокрали, и они идут домой годы, и рассказывается про их приключения, типа.

Фронт-контроллер как-то template engine должен передать вот это вот. … … Фронт-контроллер заполняет модель и возвращает `DispatcherServlet`, какое представление должно отработать, и … запустить template engine, воткнуть в него всё, чё надо воткнуть, шаблон … выбирает данные из модели… … … Не успел записать и осознать.

```java
@Controller {
    doSomething(/* принимаем чё хотим, */ Model model /* это реально мапа стрингов и объектов */) {
        // Логика …
        // Заполняем попутно модель данными.
        addAttribute("name", alex);
        return "helloPage.html";
    }
}
```

В папочке resources мы делаем папку templates — то, что не требует заполнения. Там будет обычный HTML, который ты заполнишь как-то, но ещё там будут `${name}`. То есть… Нашёл… Вставил… Вернул тебе, всё, конец Web MVC. Шаблонизаторов много разных: Thymeleaf, лист тимьяна; Mustache, усы; JSP — выглядит как веб-страница, но парсится в сервлет, а из него вызываем компонент, который парсится в страничку.
И этот механизм Spring Web MVC является стандартным, который мы используем по зависимости. «Писать на Java веб-аппликейшен — позор». Вступает в дело вопрос специализации. Всё, что отвечает за специализацию, мы писать не хотим. Если мы хотим приложение через разные интерфейсы, это, так-то, по логике внутренней одно и то же. У нас есть предрасположенность к веб-интерфейсам, то есть мобилу тоже React Native-ами. Скорее всего, веб-интерфейс у нас более приоритетный, и писать мы его будем. В Китае, к примеру, идёшь ты нафиг: сначала в мобилке всё.

У тебя должен быть доступ к одной и той же логике из разных интерфейсов. Как бы то ни было, ты должен представлять логику независимо. Если мы пишем Spring Web MVC, то эта фигня получается завязанная на вот этом вот поносе. Мы не должны думать о представлении, а вот мобильщики и веберы уже должны только думать про представление. Идеальным быть во всём нельзя: разделение на специализации. Java не как язык, а как API.

Как я понял: там, в мобилке, если ты пишешь для API Android на Java, то это стыд. А Android API тоже стыд, стыд, стыд. Моноколесо из «Саус Парка» от преподавателя-героя, который продвигал гейство, но он путь управления не предлагал — это про Android API.

Вместо этого всего тебе предлагают сделать REST-контроллер, который в body просто всё чё угодно передаёт: логику в `doSomething` и ретёрнить объект, и всё. Но тебе надо два приложения тогда: фронт, который чисто за визуал и понимание, что приходит от бэка, и бэк, который просто в JSON тебе всякое накидывает, а ты на фронте уже это читаешь и вставляешь данные. По сути, может быть любой зоопарк, который общается по HTTP, по сути.
