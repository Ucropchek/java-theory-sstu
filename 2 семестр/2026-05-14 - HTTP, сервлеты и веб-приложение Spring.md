# 14 мая 2026. HTTP, сервлеты и веб-приложение Spring - секьюритизированная версия

Конспект лекции. Главный вопрос: что происходит между обращением к URL и ответом контроллера?

## 1. От доменного имени к HTTP-запросу

У адреса `https://example.com:8443/api/films?limit=10` есть несколько частей. `https` задаёт схему, `example.com` — имя хоста, `8443` — порт, `/api/films` — путь, `limit=10` — строка запроса. Если порт не указан, обычно используются 80 для HTTP и 443 для HTTPS. DNS позволяет клиенту получить сетевой адрес по имени хоста. Адрес не обязан быть постоянным и может указывать на балансировщик, а не непосредственно на сервер приложения.

TCP доставляет упорядоченный поток байтов, но не определяет, где заканчивается запрос или что он означает. Если проектировать обмен прямо поверх TCP, правила формирования и разбора сообщений пришлось бы согласовывать самим. HTTP задаёт общий язык: методы, заголовки, коды состояния и правила передачи содержимого. Сервер может отдать готовый файл `index.html`, сформировать HTML по данным запроса или вернуть данные для другого клиента.

## 2. Что передаёт HTTP

У HTTP/1.1 запрос начинается со строки «метод, цель запроса, версия», а ответ — со строки состояния. После стартовой строки идут заголовки, пустая строка и, если предусмотрено, тело. Параметры в строке запроса, заголовки и тело — разные части, ни строка параметров, ни тело не обязательны у каждого сообщения.

```http
GET /api/films?limit=10 HTTP/1.1
Host: example.com
Accept: application/json

```

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 2

[]
```

`Accept` сообщает, какой формат клиент готов получить, а `Content-Type` — в каком формате передано содержимое. Код состояния сообщает исход операции: например, `200 OK` — успешный ответ, `201 Created` — ресурс создан, `204 No Content` — успех без тела, `400 Bad Request` — проблема с запросом, `404 Not Found` — ресурс не найден.

У HTTP/2 сохраняются методы, коды и общая семантика HTTP, но меняется способ передачи: сообщения кодируются в двоичные фреймы, а по одному соединению одновременно идут несколько независимых потоков запросов и ответов. Это мультиплексирование, а не отмена модели «запрос — ответ». Для HTTPS поддерживаемую версию клиент и сервер могут согласовать при установлении TLS-соединения. Тело сообщения в HTTP/1.1 тоже может содержать двоичные данные: текстовая там прежде всего разметка начала сообщения и заголовков.

## 3. Кто принимает запрос в Java

Servlet API появился в Java EE; в современных версиях Jakarta EE его пакеты называются `jakarta.servlet`. Сервлет — Java-компонент со стандартным контрактом, а контейнер сервлетов, например Tomcat или Jetty, управляет такими компонентами и передаёт им запросы. Nginx может стоять перед приложением как обратный прокси, но он не контейнер Java-сервлетов.

В интерфейсе `Servlet` пять методов: `init`, `service`, `destroy`, `getServletConfig` и `getServletInfo`. Основной для обработки — `service(request, response)`: через объект запроса сервлет читает данные, а через объект ответа выставляет статус, заголовки и пишет содержимое. У `HttpServlet` метод `service` направляет HTTP-методы в `doGet`, `doPost` и другие соответствующие обработчики.

Контейнер сопоставляет путь запроса с зарегистрированным сервлетом, например по записи в `WEB-INF/web.xml`, аннотации `@WebServlet` или программной регистрации. При классическом развёртывании контейнер запускают отдельно, а веб-приложение можно развернуть в нём как WAR. В обычном servlet-based приложении Spring Boot контейнер также может быть встроен в приложение и запускаться вместе с ним. DNS обрабатывает клиентская сетевая сторона, а контейнер уже принимает запрос на слушающем порту.

## 4. Ресурсное API, RPC и форматы

- В ресурсном API сначала определяется, **с чем** работаем, а HTTP-метод выражает, **что** хотим сделать. Например, `GET /api/films` читает представление коллекции, `POST /api/films` может создать новый элемент, `PUT /api/films/42` заменяет представление по известному адресу, `DELETE /api/films/42` убирает связь ресурса с этим адресом. Клиенту не нужно знать имя Java-метода или устройство базы.
- В RPC клиент обращается к именованной операции: например, `listFilms` или `createFilm`. HTTP вполне может быть транспортом для RPC. Выбор между ресурсным интерфейсом и RPC не сводится к выбору транспорта.
- Серверный веб-интерфейс может возвращать HTML, а программный API — JSON, XML или другой формат. Это разные способы использовать сервер, не взаимоисключающие типы приложений. WebSocket — отдельный протокол двустороннего обмена, а не формат представления данных наподобие JSON.
- REST — архитектурный стиль, а не синоним JSON или набора CRUD-маршрутов. В REST гипермедиа позволяют клиенту узнавать доступные действия из представлений: например, стартовый ресурс с известным URL выдаёт ссылку на коллекцию фильмов, а коллекция — ссылки на отдельные фильмы и следующую страницу. Это и есть идея HATEOAS. Имя стартового пути не обязано быть `/hello`. Ссылки снижают зависимость клиента от жёстко прописанных путей, но не отменяют контракт, понятные отношения ссылок и аккуратную совместимость. Несовместимые изменения публичного API требуют переходного плана, а не правила «никогда ничего не менять».
- SOAP использует XML-конверт, но XML не делает интерфейс SOAP, а REST не требует JSON. Синтаксическая корректность документа, соответствие схеме и выполнение бизнес-правил — три разные проверки. XML можно сверять с XSD, JSON — с JSON Schema; обе проверки надо включить явно. Например, схема может требовать строковое поле `title`, но не обязана знать, разрешено ли добавить такой фильм в конкретную коллекцию.

## 5. Путь запроса через Spring Web MVC

```text
Клиент → Tomcat → DispatcherServlet → контроллер → сервис → репозиторий
Клиент ← HTTP-ответ ← DispatcherServlet ← результат контроллера
```

`DispatcherServlet` — фронт-контроллер Spring MVC, зарегистрированный в контейнере как сервлет. Контейнер доставляет ему запрос, Spring выбирает подходящий метод контроллера, собирает аргументы, вызывает его и формирует ответ. При типичном запуске Spring Boot конфигурирует и запускает встроенный контейнер, а не наоборот.

- **Контроллер** переводит HTTP-запрос во входные данные вызова и оформляет результат. `@RequestMapping("/api/films")` на классе и `@GetMapping("/{id}")` на методе вместе задают `GET /api/films/{id}`. Для других методов есть `@PostMapping`, `@PutMapping`, `@DeleteMapping` и т. д.
- **Сервис** выполняет прикладную операцию и применяет бизнес-правила. Типичная граница транзакции — сервисный метод. `@Transactional` задаёт правила транзакции, а не «всегда делает rollback»: в обычной конфигурации откат по умолчанию происходит при непроверяемых исключениях, если транзакция действительно активна.
- **Репозиторий** инкапсулирует доступ к данным. Сущность описывает данные предметной области или их отображение в БД; **DTO** описывает то, что передаётся по API. Даже одинаковые сегодня поля не делают эти роли одинаковыми: внешнее представление не должно автоматически включать служебные поля и связи сущности. На практике маппинг пишут вручную либо используют генератор вроде MapStruct.
- `@Controller` часто используют для HTML: строка, возвращённая методом без `@ResponseBody`, может быть именем представления. `@RestController` сочетает `@Controller` и `@ResponseBody`: возвращаемый объект обычно сериализуется в тело ответа, например Jackson в JSON. Обе разновидности работают в Spring MVC.
- `ResponseEntity<T>` позволяет явно задать статус, заголовки и тело. Для обычного успешного ответа часто достаточно вернуть DTO. Повторяющуюся обработку ошибок лучше вынести в `@ExceptionHandler` или общее `@RestControllerAdvice`, а не писать одинаковые `try/catch` в каждом контроллере.

Данные приходят из разных частей запроса: `@PathVariable` читает часть пути (`/films/42`), `@RequestParam` — параметр (`?limit=10`), `@RequestHeader` — заголовок, `@RequestBody` — тело. Тело может разбираться сразу в DTO. Ограничения входного DTO можно проверять через Bean Validation (`@Valid` и ограничения полей), а прикладные правила — в сервисе. Невалидный запрос может получить `400` с понятным сообщением, не раскрывающим внутренние детали.

Нужны ли интерфейсы для сервисов и контроллеров — решение проекта, а не общее требование Spring. Интерфейс полезен, когда нужен явный контракт или несколько реализаций. Разделение HTTP-описания и реализации должно оправдывать появление второго места, которое надо поддерживать. Названия методов и классов должны объяснять их роль.

## 6. Зависимости, доступ из браузера и реактивный стек

- Для servlet-based Spring MVC выбирают соответствующий web/MVC starter в версии Spring Boot своего проекта; в типовой конфигурации он подключает MVC и встроенный Tomcat. Если приложению нужно хранилище, отдельно подбирают драйвер и слой доступа к данным. H2 может дать быструю проверку в памяти; PostgreSQL, в том числе в Testcontainers, полезен там, где важно поведение именно PostgreSQL.
- Validation, Spring Security, Kafka, Actuator/Micrometer и MapStruct решают разные задачи и не являются обязательным набором: проверка входа, безопасность, обмен сообщениями, метрики и маппинг соответственно. Код валидации нужен, даже если отдельный стартер не используется. Kafka можно использовать между компонентами асинхронно, но для приёма обычного HTTP-запроса она не нужна. Механизмы аутентификации, если они нужны, лучше держать вне прикладной логики контроллеров.
- **CORS** нужен, когда браузерный клиент с одного origin обращается к другому. Origin состоит из схемы, хоста и порта. Сервер объявляет, каким origin и при каких условиях разрешён доступ; в Spring MVC это можно настроить для отдельных маршрутов или всего приложения. Для части запросов браузер сначала отправляет `OPTIONS` (preflight). Это не перенаправление, не аутентификация и не замена защите от CSRF.
- **Реактивность** не означает автоматически ответ «задача принята» и последующую выгрузку готового результата. В Spring WebFlux работа может идти неблокирующе, а `Flux` описывает поток элементов с обратным давлением: потребитель запрашивает объём, который готов обработать. Отдельный сценарий — фоновая задача с `202 Accepted` и ссылкой на статус; его можно сделать и в обычном MVC. Чтобы получить преимущества неблокирующей цепочки, нельзя выполнять долгие блокирующие вызовы на потоке обработки событий. Для небольшого приложения с обычным JDBC/JPA MVC обычно проще.

## HTTP

HTTP определяет формат сообщения на клиента и от клиента — стандарт «вопрос — ответ».
Каждый месседж состоит из трёх частей:
- строка состояния
- параметры
- тело

Параметры и тело всегда есть вне зависимости от типа запроса. Body — просто массив байтов, бизнесовый. Строка состояния интереснее: когда мы делаем реквест, в неё идёт тип запроса: `GET`, `POST` и т. п., потом адрес — эндпоинт — ручка — URL. Ну и всякая служебная муть, номер протокола и прочее — строка состояния на запрос туда; на возврат — статус-код и служебная муть.

## URL

HTTP-протокол: чем отличается?
Автор противопоставлял HTTP и RPC. Главное — URL — Uniform Resource Locator (и URI — техническая разница) — если мы говорим за URL (у JDBC тоже URL). Когда ты обращаешься по HTTP-протоколу, ты обращаешься к ресурсу, но ты не знаешь, как он реализован. Идеологически ты говоришь: «Дай мне фильмс-лист» — я знаю, что такое лист фильмов, но я не знаю, как это реализовано. Протокол HTTP определяет взаимодействие с ресурсом. Именно поэтому появляется тип: так как именно с этим ресурсом хочется знать, что хочется сделать — какую операцию с этим ресурсом произвести (ресурс по URL) — это отличает от RPC, т. к., общаясь с ним, ты точно знаешь, к какой функции обращаешься. Соответственно, в этом же случае статус описывает результат взаимодействия с ресурсом — не нашёл = `404`. Ответы, типа, общеприняты. Никто не запрещает всегда возвращать `418` («а эм тиапот» — «я чайник»), просто зачем? Это ничего не скажет.

В целом приложения, которые так работают, можно разделить на две категории:
1. Веб-аппликейшен
2. Веб-сервис

Разница в возвращаемых ответах. Первое возвращает HTML, второе — данные.
- Если мы взглянем на попытку структурировать приложение, то у нас 3 компонента — компонент хранения, представления данных и ещё чё-то. Представление отвечает за, типа, кнопочки «для людей». Веб-аппликейшен представляет что-то человекочитаемое для человеков — такое включает в себя компонент логики и компонент представления.
А веб-сервис, видимо, нечеловекочитаемый и имеет только 2 компонента — логику и хранение данных.

Когда мы говорим о веб-аппликейшене, там начинается зоопарк: REST, SOAP, RPC («ремонт процедур»…), веб-сокеты. В REST питается JSON, а в SOAP — XML. Это архитектурная разница. Разница между JSON и XML в том факте, что у XML есть схема. В этом и факт различия SOAP и REST. И JSON, и XML могут быть well-formed. А XML может быть valid, когда JSON не valid. В XML на каждый открывающий тег есть закрывающий. Действительно ли ты правильно написал документ? Иначе не прочитать. А valid уже к бизнес-логике относится — у XML есть схема, которая описывает, какие теги есть, каких нету, какие теги в какие могут быть вложены и т. п. — и по схеме ты XML проверяешь. А в JSON схемы нету, и там всё абы как, без схемы, инструкции, и может, вообще мусор могут напихать — готов в бизнесе фильтровать всё. Разница SOAP и REST в вопросе: «А нравится ли тебе, что тебе может прийти мусор?» Типа XML неправильный, не соответствующий схеме, прийти не может. А JSON может прийти какой угодно, и никак это не отслеживаешь — пришла коробка, а что в ней — хз. Существуют кастомные валидаторы JSON со схемами — но зачем, если существует XML. Проверка схем с обеих сторон и следование им требуют ресурсов машины, но зато всё красивенько, JSON'ы — «по дешману».

REST ещё делится на два:
- REST
- RESTful
Их отличие в… Протокол REST формулируется автором так — каждый ресурс полноценно описывает себя. (Чем отличается полноценный ресурс от неполноценного?) Когда мы пишем обычный REST, мы должны откуда-то знать, куда можно постучаться — в том или ином формате должен быть документ, описывающий список ресурсов — пары вида URL с описанием типов запросов к ним и т. п. Увидеть список адресов и внутри своего приложения захардкодить. Давай представим ситуацию: ты посмотрел в этот список и захардкодил `GET filmList`. И вдруг однажды тыкаешь на кнопочку, а `filmList` нету — поменялось API с `filmList` на `listFilm`. RESTful говорит: сначала ты стучишься в `hello` — я те возвращаю список ресурсов. Из этого списка ты должен выбрать следующий ресурс и так сколько угодно хочешь. То есть ручка всегда начинается с `hello`, и как бы есть списочек продолжений от `hello`: `hello/hello2/дата база/films`.

Правило: если ты когда-то что-то кому-то показал, теперь это что-то никогда нельзя менять — оно должно всегда существовать. Удалять нельзя никогда ничего. Публичное API не имеет права меняться.

Обращение вида «респонс-реквест» в 1999 году эт норм. А в 2026 году кринжик, это уже так не работает. Протокол 2.0 призван решить кучу докачки по одному реквесту. Байтовое представление — в него можно мультиплицировать запрос. Типовой HTTP-запрос перестаёт быть человекочитаемым, т. к. становится байтовым. И клиент и сервер должны быть либо 1.x, либо 2.x.

## Лайв-стори проекта

У Spring Boot будет веб-аппликейшен-контекст — сервлеты простые аппликейшен-контексты не принимают. У нас типовое без больших данных и их туда-сюда перекидывания. Нет почвы для реактившины. Как только реактивность добавляем, то всё должно быть реактивным — вся цепочка должна быть реактивной — архитектура становится реактивной. Другой контекст — веб-контекст — `DispatcherServlet` поднимает Tomcat поднимает.

Входным компонентом у нас являются контроллеры — они отвечают за принятие запроса и возврат ответа. Золотое правило: юзеры, и мы, и все, и ревьюеры хотят быть «тупыми» — без сложностей в расшифровке написанного — всё человекочитаемое с говорящими названиями. Фронт-контроллер отрабатывает входной запрос. Сервлетная хрень работает под капотом. Делаем классик, в нём методы, отвечающие за обработку запросов, и аннотациями пометим методы, обрабатывающие запрос. `@RequestMapping` — аннотация обработки запроса. В него вписываем нашу URL, по которой будет активироваться этот метод. Там ещё всякого много: что-то на класс, что-то на методы можно повесить. На класс — `battery`, на метод — `all`, будет `battery/all`. Ещё аннотация `@RestController` — всё, что отвечает за обработку запросов, он возвращает… Web MVC — возвращает имя веб-странички, а если просто сервис, то `@RestController` (разобраться конкретнее).

Lombok’ом автогенерит всё — можно и самому, и вроде разрешено

Lombok’ом. Из полей он воткнул сервисы, JWT-сервис и класс метрик.

Мы делаем слоистую архитектуру. Поделили приложение на слои, и слои отвечают за своё. Логики в контроллерах быть не должно никогда — выносим её в сервисы, а сервисы инжектим в в контроллеры. Всё, что отвечает за БД, вынесено в репозитории. N-ное кол-во методов в контроллерах, куча методов: отдельные `PUT`, `POST` и т. п. `@GetMapping`, `@PostMapping` и т. п. — это `@RequestMapping` (метод = request POST) — всё аннотации. В интерсептерах обрабатываются JWT-токены и т. п., но и это чисто технически это в контроллерах, но логически впадлу загрязнять контроллеры.

Метод `@RequestMapping` — ходит в сервис, выполняет метод сервиса, и всё — исключение не обрабатывать в методе `@RequestMapping`. По идее, и правильно: и токены, и метод, и эксепшены в методах `@RequestMapping`, но так делать не надо (в примерном коде он формирует из метода ручки `ResponseEntity<>` и формирует `ResponseEntity` сам, и обрабатывает эксепшены внутри этого метода, и если ок, то есть `200`, то заполняет поле кода, и если не `200`, то тоже в `catch` заполняет поле кода, но это метод лошковый, сообщается, он ещё body не заполняет, если не `200`). Метод `@RequestMapping` возвращает `ResponseEntity` — если не `ResponseEntity` — значит, оно будет за него автоматически сформировано.

Что данные методы будут принимать? Можно тремя способами: хеддер, body и параметры — можем указать в нескольких местах. Есть ещё четвёртый путь — `@PathVariable` — вариации, откуда вытаскиваем данные. Определились, как вытащили данные. Валидация данных важна. Два способа: либо аннотации, либо вручную, `if/else`’ами (видимо, прямо в методе ручки).

На самом деле обрабатывать эксепшены — `@ExceptionHandler`. Мы можем перехватывать эксепшены проксей, контроллеры обернув. Рекомендуемый путь — формировать `200`, а ошибки и переформирование в `@ExceptionHandler`е.

Есть такая тема, как cross-origin — переадресация запросов — проблема в том, что это считается секурной дыркой — так работает атака с подменой запросов — по базе оно запрещено, эт надо отдельной аннотацией настраивать.

Он разделил интерфейсы и реализации, это, типа, хорошо, чисто технически мы не можем быть уверены, что нам на самом деле придёт конкретный класс — нам придёт что-то. `@Transactional` — она приводит к ролбеку — транзакции на стороне программ у нас — персистанс-менеджера — ролбек проксей, транзакция приложения — явным образом отказываемся от идеи, что у нас придёт валидный класс и говорим, что у нас приходит что-то похожее по интерфейсу — что плохо — на сервис (интерфейс, видимо), на классы разделение сделал, а на контроллеры нет — интерфейс контроллеров. Дилемма: правильно ли разделить на класс и интерфейс. И разметка на интерфейсе происходит всяким Swagger’ом и прочим — всё, что относится к описанию, висит на интерфейсе, к реализации — на классе. Единого мнения, как правильно, — разделять от на интерфейс-класс (менять всё придётся в двух местах) или нет — но надо всегда только одно выбрать для всего стиля приложения (в продах делается, как изначально делается в команде — как там уже договорились разрабы).

## Реактивное программирование

Матрица чисел — в ней чёт найти:
В REST-приложении ты держишь коннекшен 3 минуты, ждёшь, пока посчитается и тебе отправится.
В реактивном ты отказываешься отправлять всё за раз — ты их по чуть-чуть отправляешь и чуть в сторону откладываешь.
«Пришёл, показываешь задачу — присылаешь первую пачку данных, следующую пачку уже забирают у тебя сами» — один поток, который супербыстрый, отвечает только за то, чтобы вычитать все данные и вернуть сообщение, что данные получены, а второй, медленный, где всё и обрабатывается. Манифест реактивного прогерства — быстрющий ответ всегда: «Ваш сценарий принят», а отдельным процессом обрабатываем его и понимаем, что это — не кто-то принудительно запихивает нам все-все данные, а мы сами по чуть-чуть данные таскаем. (`Flux`)
